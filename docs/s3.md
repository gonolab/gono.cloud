# The S3 API

Gono Cloud speaks the S3 protocol, so that S3 clients and applications can upload files and
files can be published for anyone to download. A bucket is a folder of its owner's tree: what
is uploaded through S3 appears in WebDAV, the Nextcloud clients and the web file UI, and what is
put there through them is an S3 object.

- The administrator turns the API on and gives it a host name of its own
  ([deployment.md](deployment.md#the-s3-api), [reverse-proxy.md](reverse-proxy.md#the-s3-api)).
- Users create **access keys** and **buckets** in the S3 section of their account page
  (`/apps/account/`), or the administrator with the CLI, and decide what their buckets
  publish. The admin UI shows each user's keys and buckets and can revoke keys, make buckets
  private and remove them. Creating keys and buckets and changing what a bucket publishes is
  recorded in the audit log.

## Connecting a client

| Setting | Value |
|---|---|
| Endpoint | `s3.public_url`, for example `https://s3.example.com` |
| Region | `s3.region`, `us-east-1` unless the administrator changed it |
| Addressing | Path style: `https://s3.example.com/<bucket>/<key>`; also virtual-hosted style, `https://<bucket>.s3.example.com/<key>`, when the administrator set `s3.virtual_host_domain` (the account page shows both) |
| Credentials | An access key id (`GONO…`, 20 characters) and its secret key (40 characters), shown once when the key is created |

Signatures are AWS Signature Version 4, in headers, in presigned URLs (valid for up to seven
days) and in browser form uploads (POST policies, see below). Version 2 signatures are not
supported.

Clients can also learn these settings from the server: the capabilities
(`/ocs/v2.php/cloud/capabilities`, no sign-in needed) carry them in `gono_cloud.s3` while the S3
API is on: `endpoint`, `region`, `path_style` (always `true`), `virtual_hosted_style` and
`virtual_host_domain`, `bucket_folder`, and `anonymous` (whether buckets may publish files). The
Gono client uses them.

The examples below use path style, which always works. On a server that offers virtual-hosted
style, clients can use it instead: the AWS SDKs do by default; the AWS CLI does with
`addressing_style = virtual` (with `--endpoint-url` it uses path style otherwise), rclone with
`force_path_style = false`, and `mc` with `--path off`. Bucket names never contain dots, so one
wildcard certificate covers every bucket.

These clients are checked against every change of Gono Cloud (`acceptance/scripts/s3-clients.sh`
in its source): the AWS CLI 2 (`s3` and `s3api`), rclone and `mc`, in path and virtual-hosted
style, and restic. `mc` is archived by MinIO; its last release (`RELEASE.2025-08-13`) works.
A selection of Ceph's S3 compatibility tests (s3-tests) runs as well; the deviations it finds
in supported operations are listed, each with its reason, in `acceptance/s3-tests/` of the
source.

**AWS CLI**

```sh
aws configure set aws_access_key_id GONO...
aws configure set aws_secret_access_key ...
aws configure set region us-east-1
aws configure set default.s3.addressing_style path
aws --endpoint-url https://s3.example.com s3 ls s3://photos/
```

**rclone** (`rclone config`, or in `rclone.conf`):

```ini
[gono]
type = s3
provider = Other
access_key_id = GONO...
secret_access_key = ...
endpoint = https://s3.example.com
region = us-east-1
force_path_style = true
```

**MinIO client**

```sh
mc alias set gono https://s3.example.com GONO... <secret> --path on
mc ls gono/photos
```

**restic**

```sh
export AWS_ACCESS_KEY_ID=GONO... AWS_SECRET_ACCESS_KEY=...
restic -r s3:https://s3.example.com/backups init
```

Backup repositories work, but keep in mind that a bucket is an ordinary folder: Nextcloud
desktop clients sync it like any other folder unless it is excluded there (selective sync).

**Applications that publish media** (Mastodon, Misskey, PeerTube, image uploaders such as
PicGo): use path-style addressing, the endpoint and region above, a key with access to the
bucket, and a bucket whose anonymous access is `acl` (see below). These applications upload
public files with the `public-read` ACL; their public URL is
`https://s3.example.com/<bucket>/<key>`. What they send is checked with the libraries and
settings they use (`acceptance/scripts/s3-apps.sh` in the source):

| Application | Settings |
|---|---|
| Mastodon | `S3_ENABLED=true`, `S3_ENDPOINT=https://s3.example.com`, `S3_HOSTNAME=s3.example.com`, `S3_BUCKET`, `S3_REGION=us-east-1`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` (with an endpoint, Mastodon uses path style; `S3_PERMISSION` stays `public-read`) |
| Misskey | Object storage on, endpoint `s3.example.com`, region `us-east-1`, bucket, "Use SSL", "s3ForcePathStyle", "Set public-read on upload", base URL `https://s3.example.com/<bucket>` |
| PeerTube | `object_storage`: `enabled: true`, `endpoint: 's3.example.com'`, `region: 'us-east-1'`, `force_path_style: true` (or virtual-hosted style, see above), `upload_acl.public: 'public-read'`, `upload_acl.private: 'private'`, the key in `credentials`, and the `bucket_name` of each section (one bucket with the sections' prefixes works) |
| PicGo | Plugin `picgo-plugin-s3` (uploader "Amazon S3"): endpoint `https://s3.example.com`, region `us-east-1`, bucket, `pathStyleAccess: true`, `acl: public-read` |

## Access keys

A key acts as its account. It reaches either every bucket of the account (with full access,
present and future buckets alike; only such a key may create and delete buckets or change what
a bucket publishes, with its ACL or policy) or the buckets it was granted, each read only
(`view`) or read and write (`full`). A key can expire, and it can be revoked at any time.

Access keys are not app passwords: they do not sign in to WebDAV, and app passwords do not sign
S3 requests. The server stores the secret encrypted with its key file (`two_factor.key_file`),
because S3 signatures need it.

## Buckets

- **Names** are 3 to 63 characters from `a-z`, `0-9` and `-`, starting and ending with a
  letter or digit, and unique on the server.
- **Creating** a bucket (account page, `gono-cloud s3 bucket create`, or `CreateBucket`)
  creates the folder `Buckets/<name>` (`s3.bucket_folder`). An existing folder becomes a bucket
  by **binding** it (account page, `gono-cloud s3 bucket bind`); its files are objects at once.
- **Creating it again** with `CreateBucket` answers as S3 does in the server's region: in
  `us-east-1` (the default) with success, setting what the bucket publishes to the request's
  canned ACL like `PutBucketAcl` (no ACL: `private`, so a published bucket stops publishing);
  in every other region with `409 BucketAlreadyOwnedByYou`, changing nothing. Its files stay.
- A bucket follows its folder when the folder is renamed or moved, and disappears when the
  folder is deleted.
- **Removing** a bucket on the account page or with `gono-cloud s3 bucket unbind` keeps the
  folder and its files. `DeleteBucket` through S3 needs an empty bucket and removes the folder
  as well.

## Keys and files

An object's key is its path below the bucket's folder. Keys the file tree cannot hold are
refused rather than rewritten:

- empty segments (`a//b`, a leading `/`), `.` and `..`, NUL, and segments longer than 255
  bytes;
- a key that names a folder (`photos` while `photos/a.jpg` exists), or one below a file
  (`a.jpg/b`), answers `409 KeyConflict`.

**Unicode spelling.** Keys need not be in Unicode NFC; file names from older macOS systems are
in NFD (`e` followed by a combining accent instead of `é`), and the AWS CLI, rclone and `mc`
send them as they are. The tree stores names in NFC, so WebDAV and the Nextcloud clients see
`Café`, while S3 keeps the key as it was written: listings return those bytes, in their byte
order, and the object answers only to that spelling (a `GET` of the NFC form is `404`), so sync
tools find what they uploaded and transfer nothing the next time. Files that WebDAV writes into
a folder S3 spelled that way are spelled like it; a WebDAV rename gives the NFC name. One
difference to S3 remains: two keys that differ only in normalization, in any segment
(`Café/a.txt` in NFC and in NFD, or `Café/b.txt` in NFC next to an NFD folder), would be one
file, so the second answers `409 KeyConflict` while the first is stored. A folder with no file
below it holds no key and takes the new spelling.

A key ending in `/` with an empty body creates a folder (a "folder marker"). Deleting an object
never removes folders, and listings never show empty folders, as in S3.

The ETag of an object uploaded in one request is the MD5 of its content; of a multipart upload,
the MD5 of the parts' MD5s followed by `-<parts>`. Files written another way (WebDAV, the
Nextcloud clients, the web file UI) get the MD5 of their content too, computed as they are
written, so sync tools such as rclone can compare it with local files. A file whose MD5 is not
known has its WebDAV ETag as its S3 ETag: one written before Gono Cloud recorded MD5s, or
changed on the server's disk outside Gono Cloud, until `gono-cloud rescan --checksums` fills
them in. Content types, `Cache-Control`,
`x-amz-meta-*` and the like are kept with an object until it is overwritten other than through
S3. Files written through WebDAV get a content type from their name.

Sync tools keep a file's modification time in the metadata `mtime` (`X-Amz-Meta-Mtime`; rclone,
s3fs and others): UNIX seconds, with a fraction for rclone. Gono Cloud makes it the file's
modification time on `PutObject`, form uploads, multipart uploads (named at
`CreateMultipartUpload`) and `CopyObject` (rclone changes the time by copying an object onto
itself), so WebDAV and the Nextcloud clients show the original time; S3's `Last-Modified` is
that time too. The metadata itself is kept as sent. Values that are not such a time are
metadata only.

Files locked by a WebDAV client (`LOCK`) cannot be written through S3 meanwhile
(`409 OperationAborted`).

## Browser applications

Web pages on other sites can talk to a bucket directly (uploads with presigned URLs or forms,
downloads with `fetch`) once the bucket has **CORS rules**. Rules are set through the S3 API with
a key that has full access to the bucket, for example with the AWS CLI:

```sh
cat > cors.json <<'JSON'
{"CORSRules": [{
  "AllowedOrigins": ["https://app.example.com"],
  "AllowedMethods": ["GET", "PUT", "POST"],
  "AllowedHeaders": ["*"],
  "ExposeHeaders": ["ETag"],
  "MaxAgeSeconds": 3000
}]}
JSON
aws --endpoint-url https://s3.example.com s3api put-bucket-cors --bucket photos \
  --cors-configuration file://cors.json
```

They work as in S3: up to 100 rules; `AllowedOrigin` and `AllowedHeader` may hold one `*`;
methods are `GET`, `PUT`, `HEAD`, `POST` and `DELETE`; the first rule that allows a request
answers it. Preflight requests (`OPTIONS`) need no signature. Multipart uploads from a browser
need `ETag` among the exposed headers. `GetBucketCors` reads the rules and `DeleteBucketCors`
removes them; the account page shows how many a bucket has. CORS rules allow nothing by
themselves: a page can only read what its request was allowed to do anyway, with a key or as a
published object.

**Form uploads** (`POST` to `https://s3.example.com/<bucket>` with `multipart/form-data`, a
policy and a SigV4 signature of it, as built for example by boto3's `generate_presigned_post`)
upload one file as the key that signed the policy. The policy's conditions are checked
(`key`, `bucket`, `content-length-range`, `success_action_status` and every other field), and
the fields `acl`, `Content-Type`, `Cache-Control`, `x-amz-meta-*` and the like apply as for
`PutObject`. As in S3, the file must be the form's last field. The request must state its
length (`Content-Length`), as browsers do. A form without a signature is an anonymous write and
is refused.

## Publishing files

Anonymous requests (without a signature) are refused unless the administrator allows them
(`s3.allow_anonymous`). Then each bucket's owner chooses what it publishes:

| Anonymous access | Who may download | Set with |
|---|---|---|
| `private` | nobody (the default) | the account page, `gono-cloud s3 bucket set`, or `PutBucketAcl` with `private` |
| `acl` | objects uploaded or set with the canned ACL `public-read` | the account page or `gono-cloud s3 bucket set` |
| `public-read` | every object in the bucket, whoever put it there | the account page, `gono-cloud s3 bucket set`, `PutBucketAcl` with `public-read`, or the download policy (below) |

A bucket can also allow anonymous **listings**; a listing shows every key of the bucket, private
ones included.

**Bucket policies.** Gono Cloud keeps no policy documents, but it understands the one policy
that tools write to publish a bucket, `mc anonymous set download`'s: everyone may
`s3:GetObject` every object (`arn:aws:s3:::<bucket>/*`), and optionally `s3:ListBucket` and
`s3:GetBucketLocation` on the bucket. `PutBucketPolicy` with it makes the bucket `public-read`,
with anonymous listing if the policy allows `s3:ListBucket`. `DeleteBucketPolicy`
(`mc anonymous set none`) turns listing off and makes a `public-read` bucket private (an `acl`
bucket keeps publishing its public-read objects). `GetBucketPolicy` (`mc anonymous get`)
answers with the policy that describes what the bucket publishes now, or
`NoSuchBucketPolicy`. Every other policy, such as `mc anonymous set upload` or `public`
(anonymous writes), one for a prefix, for named principals or with conditions, answers
`501 NotImplemented` and changes nothing. Setting and deleting policies needs a key with full
access to every bucket, like `PutBucketAcl`.

- Anonymous requests may only read (`GetObject`, `HeadObject`) and, where allowed, list. Every
  refusal is `403 AccessDenied`, also for objects that do not exist.
- An object uploaded with `x-amz-acl: public-read` into a bucket that publishes nothing is
  refused (`AccessControlListNotSupported`), so an application learns at once that its links
  would not work.
- Overwriting a public object through WebDAV or the web file UI makes it private again (in an
  `acl` bucket).
- Anonymous responses carry `X-Content-Type-Options: nosniff`. The S3 host name is never the
  site's, so uploaded pages do not run as part of it.
- The web file UI offers **Copy public link** (in a file's menu, and on its page) for every file
  anyone can download right now: in a `public-read` bucket, or with the `public-read` ACL in an
  `acl` bucket, while the administrator allows anonymous access. The link is
  `https://s3.example.com/<bucket>/<key>`, or `https://<bucket>.s3.example.com/<key>` with
  virtual-hosted style, which gives each bucket an origin of its own.

## Operations

| Area | Supported |
|---|---|
| Service | `ListBuckets`, with `prefix` and pages (`max-buckets`, `continuation-token`) |
| Buckets | `CreateBucket`, `DeleteBucket`, `HeadBucket`, `GetBucketLocation`, `GetBucketVersioning` (never enabled), `GetBucketAcl`, `PutBucketAcl` (canned `private`, `public-read`), `PutBucketCors`, `GetBucketCors`, `DeleteBucketCors`, `PutBucketPolicy`, `GetBucketPolicy`, `GetBucketPolicyStatus`, `DeleteBucketPolicy` (the download policy only) |
| Listings | `ListObjectsV2`, `ListObjects`, with prefixes, any delimiter, `encoding-type=url`; `ListObjectVersions` lists every object as its only version, `null`, as S3 does for a bucket that never had versioning (cleanup tools use it), and `versionId=null` reads and deletes the object |
| Objects | `PutObject`, `PostObject` (browser form uploads), `GetObject` (ranges, `partNumber`, conditional headers, `response-*` for signed requests), `HeadObject` (`partNumber` too), `GetObjectAttributes` (`ETag`, `Checksum`, `ObjectParts`, `ObjectSize`, `StorageClass`), `DeleteObject`, `DeleteObjects`, `CopyObject` (`COPY` and `REPLACE` metadata), `GetObjectAcl`, `PutObjectAcl` (canned) |
| Conditional writes | `If-None-Match: *` (create only), `If-None-Match` with an ETag (anything but that version), `If-Match` with an ETag (that version only) and `If-Match: *` (any existing object) on `PutObject`, `CopyObject` and `CompleteMultipartUpload`; `If-Match` on a missing object answers `404 NoSuchKey`, every other failed condition `412` |
| Integrity | `Content-MD5`, `x-amz-content-sha256`, and `x-amz-checksum-*` (CRC32, CRC32C, CRC64NVME, SHA-1, SHA-256 and more) in headers or `aws-chunked` trailers; multipart uploads with a checksum algorithm and type (below) |
| Multipart uploads | `CreateMultipartUpload`, `UploadPart`, `UploadPartCopy` (a whole object or a byte range of one, from any bucket the key may read, with the `x-amz-copy-source-if-*` conditions), `ListParts`, `CompleteMultipartUpload`, `AbortMultipartUpload`, `ListMultipartUploads` (without a delimiter). Parts are 1 to 10000, all but the last at least 5 MiB. Uploads not completed within `s3.multipart_ttl_secs` of their last part (a week) are removed. A completion repeated with the same parts within a day (a client retrying after a lost answer) gets the first answer again, as from S3; conditions (`If-None-Match: *`, `If-Match`) are checked before the answer starts, so a failed one is a plain `412`. Completing does not copy the first part (its file becomes the object) and, on Linux, copies the others in the kernel, which shares their data on file systems with reflinks (XFS, btrfs) instead of writing it again. |

Every response carries a request id (`x-amz-request-id`), and every error document names it
(`RequestId`); the server's log line of the request (`s3 request`, at level `info`) records it
as `request_id`, so an error a client reports can be found there.

**Multipart checksums.** A multipart upload created with a checksum algorithm
(`x-amz-checksum-algorithm`: CRC32, CRC32C, CRC64NVME, SHA1 or SHA256, as current AWS SDKs and
the AWS CLI send by default) gets every part's checksum in it, computed by the server and
compared with the one the client sent, and the object gets a checksum derived from its parts:
`FULL_OBJECT` (CRC32, CRC32C, CRC64NVME; the CRC of the whole content, combined from the parts'
CRCs) or `COMPOSITE` (the checksum of the parts' checksums, followed by `-<parts>`; the default
for every algorithm but CRC64NVME), as `x-amz-checksum-type` says. A completion that names
the object's checksum or a part's must match it (`BadDigest`, `InvalidPart`). Objects written
by a multipart upload keep their parts: `GetObject` and `HeadObject` with `partNumber` read one
part (its range, `x-amz-mp-parts-count`, its checksum), and `GetObjectAttributes` lists them.
Parts are numbered 1 to their count in the object's order, whatever numbers they were
uploaded with. Any other file is its own and only part; a part number an object does not
have answers `416 InvalidPartNumber`. Written through WebDAV, a file loses its parts and
checksum with the rest of its S3 metadata.

Everything else answers `501 NotImplemented`: versioning, lifecycle rules, object lock,
server-side encryption, tagging, other bucket policies, website hosting.
